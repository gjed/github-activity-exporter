# Grafana dashboards

Two dashboards are generated from the registry by `make generate` ([#19](https://github.com/gjed/github-activity-exporter/issues/19), [#90](https://github.com/gjed/github-activity-exporter/issues/90)):

- `dashboards/github-activity.json`, GitHub Activity: the `github.*` and `renovate.*` metrics, PR, issue and Dependency Dashboard activity.
- `dashboards/github-activity-exporter.json`, GitHub Activity Exporter internals: the exporter itself, every `github_exporter.*` metric (collection cycles and overruns, GitHub API errors, secondary rate limits, rate limit headroom per pool, OTLP push errors) and the [self-telemetry metrics](self-telemetry.md#self-telemetry-metrics).

`make generate` fails if the GitHub Activity dashboard queries any other metric, or if a `github_exporter.*` metric has no panel on the exporter dashboard. Every query uses the name and type each metric declares in `annotations.prometheus`, in UTF-8 PromQL syntax (`{"github.pr.count", job=~"$job"}`): counters through `rate`, histograms through `histogram_quantile` over `_bucket`, gauges through `last_over_time`, reduced with `max by` the metric's identity (`job`, `exporter.target` and the attributes the registry declares on it) before the panel's own aggregation. The old and new pod of a restart write separate series, which differ in `instance` and the other per-process resource labels; inside one window the identity reduction counts them once, and shows the larger value while both are in the window. Exporter Deployments that share a `job` therefore show the largest process on the self-telemetry gauges, not the sum: give each its own `service.name` or `service.namespace` to tell them apart. Every panel's Min interval is the hidden constant variable `$min_step`, default `10m`. It must be at least twice `export.interval`, so each window holds two pushes, and twice `collection_interval`, so each window holds a cycle: `histogram_quantile` panels need a new observation in the window, `rate` and `last_over_time` panels only the pushes. The default fits the defaults (60s and 5m). With a longer interval, raise `$min_step` in the dashboard settings or with the chart's `dashboard.minStep`. It needs the [backend settings](../README.md#backend-requirements) for the [metric names](metrics.md#metric-naming).

Variables of both: data source, `job` (the exporter's `service.name`, `github-activity-exporter`, optionally prefixed with `service.namespace/`) and `exporter.target`; the GitHub Activity dashboard adds `github.org` and `github.repo`. Its `job` and `exporter.target` come from the series of its own panels, never from a `github_exporter.*` or self-telemetry metric, so a target is listed as soon as any of its panels has data, whichever collectors the target enables. The exporter dashboard takes them from `github_exporter.scrape.duration`, recorded for every target. The Dependency Dashboard row shows no data unless a target enables `renovate_dashboard`, and the PR size by author panel none unless a target sets `collection.pr_author`. The exporter dashboard's Self-telemetry row (Go memory, heap allocation rate, goroutines, GitHub API latency p50 and p90 by `url.template` and status) shows no data unless [self-telemetry metrics](self-telemetry.md#self-telemetry-metrics) are active. Every other panel of both dashboards has data with them off.

`make test-e2e` (Docker required) runs the exporter twice, with self-telemetry metrics on and off, against a mock GitHub API, pushes OTLP into Prometheus 3.x, and runs every query of every generated dashboard. Its target sets `collection.pr_author`. It fails if a query errors or returns no data, or, with self-telemetry metrics off, if a Self-telemetry panel returns data.
